## Iggy / Flash — Cutscenes and Mouse Only

**iggy_w32.dll** is used ONLY for:
1. Playing Flash SWF cutscenes (FMV / opening movies)
2. Handling mouse cursor input

It is NOT involved in any UI rendering. All menus, save/load screens, battle UI,
field UI, text boxes, and cursor logic are native C++ code (TkMenu/TkWindow system).

**When reverse engineering UI**: do not hook iggy exports — they will not fire for
menu/cursor/text events. Look at native TkMenu/TkWindow/game functions instead.

**Flash SWFs** bundled with the game contain only visual assets (fonts, shapes, sprites)
plus cutscene content. They do NOT contain interactive UI logic. Some UI screens
(e.g., save/load) call `showX` SWF functions, but this is just to display the
visual asset frame — the actual UI text, cursor, and navigation are native code
running alongside.

## PInput Device System

- node[0]: pointer to next node

deviceObj+0x14.

## Title Screen Architecture (Corrected)

The title screen runs in a BLOCKING while loop in FUN_00641870, BEFORE the main game loop

### Entity ID Ranges

**chr_id is polymorphic** (RE finding, session 41+):

- **Lower 12 bits (`& 0xfff`)**: Index into the `w_name` resource table (model name lookup). Range 0x000–0xFFF. The mod's existing FUN_007a0c70 wrapper (RVA 0x7A0C70) takes `chrId & 0xfff` as input.
- **Upper nibble (`& 0xf000`)**: Category flag. The engine dispatches on this nibble at `decompile/layer4_menu_font_native.txt:19670–19681`:
The native classification reads the unsigned 16-bit entity identifier at actor offset 0x21A and isolates its high nibble with mask 0xF000. Category 0x5000 selects engine objects; 0x2000 has its own category branch, while 0x0xxx and 0x1xxx fall through the lower-category path. The recovered branches compare the masked value with upper bounds 0x5001 and 0x2001. Keep these build-specific facts distinct from inferred entity labels.
  Engine-confirmed branches: `0x0xxx`, `0x1xxx` (shared), `0x2xxx`, `0x5xxx`. **No engine-side dispatch found for `0x3xxx` or `0x4xxx`** — those ranges may exist for some purpose but the meaning isn't proven from RE alone.

| Range | Meaning | Confidence | Source |
|-------|---------|-----------|--------|
| `0x5000–0x5046` | Engine object class tags (returned by property classifier `FUN_007a1c20` at RVA 0x7A1C20) | 0.98 | `decompile/layer2_game_logic.txt:320552–320881` |
| `0x5001` | Save Sphere | 1.0 | classifier returns this when property bit `& 8` set; consumer at `decompile/layer2_game_logic.txt:478857` |

#### Engine-unproven (do NOT classify in production)

- `0x0013–0x1FFF`: Unknown. Engine has a dispatch branch for `0x0xxx`/`0x1xxx` but the semantic meaning isn't extractable from RE. Rikku appearing as a stationary NPC in the Thunder Plains tutorial has chrId `0x29` — this falls in this range but was identified empirically by the user, not from engine code. **Do not assume "all 0x13–0x1FFF = NPC"** — that was attempted and reverted (see `src/navigation/index.js:103` history).
- `0x2000–0x4FFF`: Documented as "NPC range" in older notes (sourced from Fahrenheit `Ids/NpcId.cs`), but no engine code dispatches on the entire range as NPCs; it checks only whether the upper nibble equals 0x2000. Use cautiously; the Fahrenheit-sourced range is a community-RE claim, not first-party engine evidence.

#### Path forward (if classification authority is needed)

Two approaches that would yield ≥0.9 confidence:

1. Find a static `.rdata` lookup table indexed by chrId that gives a category byte/string per ID. The `w_name` resource at RVA 0xB54E34 (~150KB) is one such table — its full structure across all 4096 indices isn't yet decoded. If it contains a category prefix per entry (`'c'`/`'n'`/`'m'`/`'f'` etc., per the model-name dispatch at `decompile/layer2_game_logic.txt:392274–392303`), reading it once at module init resolves the entire chrId space.
2. Find the actor-spawner / actor-init function that reads chrId and dispatches by category. Its switch ranges are authoritative.

Neither has been completed.

### BtlWindow Per-Type Cursor Handler Dispatch

### Action-exec state model (runtime-confirmed, sessions 28-34)
Per-actor state bytes in the 0xF90 struct:

| Offset | Meaning |
|--------|---------|
| +0xDF0 | Action lifecycle byte: 0 is idle, 3 is the execution phase (animation, banner and script), and 5 is the brief finalize marker. |
| +0xDFB | Action-type discriminant: 0 during a basic-attack execution; 5 during named abilities such as spells, Overdrives and enemy abilities. Session 34's Stalker capture showed Tidus's basic attack and Lulu's Fire sharing the lifecycle while this value differed. |

### Battle command data resolver: FUN_0079a4c0 (MsGetComData)
RVA `0x39A4C0` (Ghidra `0x0079a4c0`). 207 bytes. Session 38
probe-verified universal battle-command data resolver — every battle
UI text draw flows through this. Signature:

FUN_0079a4c0 (MsGetComData) accepts an unsigned command ID and an output location for the command-data base; it returns a pointer to the resolved entry. See the native resolver at the location in this section heading.

- `cmdId` — 16-bit command ID. Top 4 bits = type prefix, low 12 bits = row.
- `out_base` — optional (NULL-safe). Filled with the base address used
  to compute the text pointer.
- Returns — pointer to the command's data entry (or sentinel
  `&DAT_01136000` for prefix-0/5/7/0xA/0xB which have no real entry struct).

Prefix dispatch:
| Prefix | Handler | Meaning |
|--------|---------|---------|
| 0x0 | FUN_0079af20 | Player misc text row (sets out_base only) |
| 0x2 | FUN_00790a40 | Item entry |
| 0x3 | FUN_00790ae0 | **Player ability** (Fire, Cure, Attack, Overdrive commands) |
| 0x4 | FUN_00790aa0 | (unresolved; some enemy-skill path?) |
| 0x5 / 0x7 / 0xB | FUN_007abe10 | Range-table text lookup via sentinel |
| 0x6 | FUN_00790ac0 | **Monster ability** (Bite, 1000 Needles, etc.) |
| 0x8 | FUN_007909c0 | Item row (alt) |
| 0xA | FUN_007908b0 | Base-only |

Caller text-offset convention varies:
- **K=0 ("k0")**: text = the unsigned 16-bit offset at entry added to out_base — used by
  `FUN_00898bd0` (banner draw, the short name), `FUN_00895290`
  (Learning popup).
- **K=8 ("k8")**: text = the unsigned 16-bit offset at entry byte 8 added to out_base — used by
  `FUN_008998e0`, `FUN_00899730` (help panel writers, the description).

Session 38 probe decoded both offsets for each caller. For banner
draws, k0 is the NAME ("Fire", "Bomb Fragment") and k8 is the
DESCRIPTION ("Deals fire damage to an enemy.").

### Action banner draw: FUN_00898bd0
RVA `0x498BD0` (Ghidra `0x00898bd0`). 59 bytes. Session 38
probe-verified banner function — fires exactly once per action that
displays a banner, for any actor class (party, summon, enemy) and
any command prefix. Hooked in production at `src/battle/actions.js`.

FUN_00898bd0 resolves the 16-bit command ID through MsGetComData (FUN_0079a4c0). Bit 2 at entry offset 0x1C is the has-banner flag: if absent, the function reports no banner. Otherwise it combines the entry’s first text offset with the resolved base and submits the name to display slot 1 through FUN_0089db10, then reports success.

- Reads `entry[0]` (ushort, the k0 name offset).
- Gated on flag bit `entry[+0x1c] & 4` — commands without this bit
  never banner.
- Unique caller: `FUN_0078fef0` (RVA 0x38FEF0). That wrapper is what
  Atel scripts (or the action dispatcher) invoke to set up a banner;
  it takes (cmdId, actor_byte) and stores the actor_byte into
  `DAT_0112c9d1/9d2` so the banner renderer knows who it's for.
- Probe-confirmed fires (session 38): Rikku+Bomb Fragment (item 0x201a),
  Lulu+Fire (spell 0x3042), Valefor+Sonic Wings (ability 0x30cc).
- NOT called by menu renderers — menu-cursor text goes through
  MsGetComData via different callers (0x49ac45, 0x4a66cf, 0x4998f3
  etc.), never through 0x498BD0. This makes the hook a clean signal.

### Map Name Resolver — `FUN_0086c3c0` + `FUN_006460e0` (session 41)

The save/load screen converts an area-name index (not a room ID) to a human-readable area name

### FFX Text Control Code 0x13 — Character Name Substitution
In the HELP buffer (and possibly other text), byte 0x13 followed by a byte means
"insert character name here". The character index = (next_byte - 0x30).

##### Loc-string resolver (proven safe to call from mod-side)

- FUN_006414A0 using loc_id, buf, bufsz — RVA `0x2414A0`. **`__cdecl`**.
  Internally:
  - calls FUN_006DB1A0 -> returns `DAT_00CDED48` = sLanguageManager
    singleton (panics if not initialized yet).
  - calls FUN_006DB320 using loc_id, buf, bufsz — `__thiscall` on the singleton
    (compiler emits copy the object pointer from EAX into ECX before making the call). FUN_006414A0 wraps the ECX
    setup, so callers don't need to manage it.
- `FUN_006DB320` — RVA `0x2DB320`. Walks the language-table buffer at
  the language-table buffer pointer stored at this offset 0x14 (size at `+0x18`), counting `\n` separators. Copies line
  `loc_id` (zero-indexed) to `buf` as plain ASCII.
  **Caller MUST zero the destination buffer before each call.** Runtime
  evidence (session 58, FFX_SR_Latest.log byte inspection) showed that
  when a shorter string is written into a buffer that previously held a
  longer string, leftover bytes past the new content's last byte remain
  intact — readCString using bufsz walks past the new content into them.
  Repro: "Change System Settings" then "Resume Game" → readback was
  "Resume Gamem Settings". The decompile suggested null-termination at
  the new length; runtime contradicts. Whether the writer never zero-
  terminates at all or only does so under specific conditions is
  undetermined — the safe rule is to wipe the buffer before the call.
- Singleton init: `DAT_00CDED48` (RVA 0x8DED48) — must be non-zero before
  calling.

This means **the mod can call FUN_006414A0(loc_id, buf, 256) directly** to
resolve any loc string without ECX gymnastics. Address is RVA 0x2414A0.

##### Cursor-change event chain (CONFIRMED by decompile)

When the user moves the cursor in any ESC sub-page:
1. `FUN_00690130` per-frame detects the input direction, calls
   callFlash using 0, "prevItem", ... or `(0,"nextItem",...)` etc.
2. Flash advances its focused item, and dispatches **`EscMenuHelpTextRefresh`**
   back to C++ with payload = a 2-element Iggy array.
3. FUN_0068E730 EscMenuHelpTextRefresh using menu, ev:
   - `__RTDynamicCast` on `param_1` to confirm FFEscMenu (and reads
     the guard value stored at self offset 0xEC — bails if non-zero).
   - Builds a stack-local IggyValuePath from the event payload via
     `FUN_00A28D10` (gets player) + `FUN_00A288B0` (PathFromRef).
   - Reads sVar1 receives FUN_00A28B20 using 0 (path-element 0 as S32).
   - Reads sVar2 receives FUN_00A28B20 using 1 (path-element 1 as S32).
     **(sVar1, sVar2) is the (page-tag, item-tag) pair Flash assigns
     to each focusable item — they are NOT zero-based indices. The
     specific values are defined inside `escmenu.swf` and are stable
     IDs the C++ side matches against `DAT_00C33DB8` table.**
   - Iterates 35 entries at `&DAT_00C33DB8` (each entry 8 bytes:
     `uint32 help_loc_id`, `int16 sVar1_match`, `int16 sVar2_match`).
     On match, schedules FUN_00A28DF0 using FUN_0068E6E0, the address of entry — a
     deferred task on the Iggy player thread.
   - Default fallback: `&DAT_00C33DB0` (one stable default loc id).
4. Eventually FUN_0068E6E0 using loc_id_ptr runs:
  - FUN_006414A0 resolves the localization ID supplied by loc_id_ptr into the
     256-byte help buffer at instance offset +0x121 — copies
     the localized help text into the FFEscMenu instance buffer at
     offset +0x121 of the instance referenced by DAT_00CCC868 (256-byte buffer).
   - Sets the countdown field at self offset 0x224 to five — countdown for the per-frame `setHelpText`
     to push it to Flash.
5. `FUN_00690130` next frame, when countdown hits 0, calls Flash's
   `setHelpText` with the content of `+0x121`.

##### Read-path implication

The C++ side never holds the **labels** ("Resume", "Save & Quit") after init —
they live only in Flash storage. After init, the only text the C++ side
re-resolves on cursor move is the **help text** (description string), via
the chain `EscMenuHelpTextRefresh` → `FUN_0068E6E0` → `FUN_006414A0`.

This means a clean v1 read path announces the **help text** on every cursor
move (a hook on `FUN_0068E6E0` reads the loc-id pointer and resolves it via
FUN_006414A0 using the value pointed to by ptr, buf, 256). For label-text v2 we'd capture labels
during init by hooking `FUN_00A28BA0 IggyMenu::callFlash` filtered to
`setHomePage`/`setSysSettingPage`/etc. and parsing the IggyValue array;
mapping (sVar1, sVar2) → page index + item index requires runtime
evidence we don't yet have (the Flash-side IDs are not derivable from the
binary alone).

## Exit Trigger System

Atel workers with types 2, 3, 5, or 6 are trigger objects placed on maps.

### Finding Triggers at Runtime
1. Read Atel controller: the pointer stored at RVA 0xF26AE8 → controller
2. Actor count: `controller + 0x0C` (U16)
3. For each index: call FUN_0086a7c0 using index (RVA 0x46A7C0) → worker pointer
4. Read type: the first byte reached by dereferencing the worker’s first pointer — first byte of value at worker's first dword

## Save/Load Screen (TK state machine)

Save/load is **TK-driven**, consistent with the project rule that
Iggy/Flash is animation + mouse only and all menus are TK. The state
machine, cursor, and input dispatch all live in TK code; the save/load SWF
exists purely to render visuals from TK-pushed data.

### State machine
- `DAT_00CE72D8` (RVA 0x8E72D8) — save/load state register
- `DAT_00CE72F0` (RVA 0x8E72F0) — Yes/No popup cursor (0=button1, 1=button2)
- State-handler functions in the FUN_006EFxxxx-FUN_006F0xxxx range:
  - `FUN_006EFD90` (RVA 0x2EFD90) — Yes/No popup input handler A
  - `FUN_006F00E0` (RVA 0x2F00E0) — Yes/No popup input handler B
  - `FUN_006F06F0` (RVA 0x2F06F0) — Yes/No popup input handler C
  Each reads input via `FUN_006EF460`, branches on event type
  (3=Up, 4=Down, 7=Confirm, 8=Cancel), and on Up/Down does
  reverses the Yes/No cursor value stored in `DAT_00CE72F0`.

### TK helpers (resolve loc → buffer, then mirror to Flash)
These are TK functions in FFX.exe. The buffer write happens BEFORE the
Flash mirror call, so the resolved data is always TK-source — the

## Event-Message System (event-script choice prompts + cutscene subtitle list)

**Header note (corrected session 52):** This pipeline is for the
event-message LIST at `DAT_0112A01C` — sub-menu / choice-prompt /
event-script-bundle entries. **It is NOT the interactive NPC dialogue
path.** Interactive NPC dialogue uses the message-window pool at
`DAT_018676B0` and is installed via `FUN_008B8980`. See "Message
Window System" below.

The event-message system is separate from the TkWindow / MsMenuGetText menu
systems. Event-script choice prompts and list entries route through this
pipeline. Generic FMV coverage was a historical pending test: ordinary movies
can use TK dialogue, while the post-game timed captions bypass this decoder.
See the 2026-10-05 movie-caption section above.

### Pipeline
1. `TKMallocAndReadEventMessage` (RVA 0x48CA30) — loads a `.bin` event
   message file from `obj_ps3/<name>.bin` (or `kernel/<name>.bin` for
   monsters, `btl/<name>/<name>.bin` for battle, `menu/<name>.dcp` for
   macros). Per-language path: `jppc/`, `uspc/`, `frpc/`, `sppc/`,
   `depc/`, `itpc/`, `krpc/`, `chpc/`. Called once per event/cutscene to
   load the bundle.
2. Per-frame, the event renderers walk the loaded message list:
   - `FUN_0076F580` (RVA 0x36F580) — primary event renderer, void using void
   - `FUN_0076F960` (RVA 0x36F960) — secondary renderer (long-form events)
   Both read DAT_0112A01C (message-list base), DAT_0112A088 (current
   message index), DAT_0112A03C (message-table base).
3. Each renderer calls `FUN_00776A50` (RVA 0x376A50) — **the dialogue
   decoder** — to decode the active script line into FFX charset.

### `FUN_00776A50` — dialogue decoder
- Signature: void FUN_00776A50 using the value pointed to by out, the value pointed to by in, flags, the value pointed to by p4, the value pointed to by p5
- Reads raw script bytes from `in`, writes FFX-charset bytes to `out`,
  null-terminating on return.
- Output normally targets DAT_0112A02C (allocated 0x4000 = 16KB at startup
  via FUN_00774D10 using 1, 0x4000) or a sub-offset within it.
- Output format is the same FFX charset used by menu text — `decodeFFXSegments`
  handles it directly.
- Opcodes processed (don't write to output unless noted):
  - `0x13` — character-name reference: writes `0x13` + chr-id (2 bytes)
  - `0x0B` — special: writes `0x0B` + byte (2 bytes)
  - `-0xff5` (signed-short pattern) — set value (callback or DAT_0112A0A4 write)
  - `-0xef5` / `-0xcf5` / `-0xdf5` — conditional skip / nesting
  - `-0xbf5` — recursive sub-decode via `FUN_00774970`
  - `-0x9f5` / `-0x7f5` — output formatters (callbacks via DAT_00C416C0/CC)
  - `-0x8f5` — sets DAT_0112A084 and marks the early-return output flag
  - `-0x5f5` — sets the secondary output flag
  - default — passes character bytes through (1 or 2 byte form)
- Buffer-overrun guard: FUN_0090AE50 emits the retained error text when the
  output buffer has reached the 0x3FFF-byte limit from its base.
- Idempotent on same input: per-frame typewriter calls produce identical
  output, so a string-diff against last-spoken eliminates duplicate
  announcements.

### `FUN_008B5D70` — TODrawMessage (per-slot per-frame draw)
- Caller: `FUN_008ABCE0` (TODrawMessageWindow, RVA 0x4ABCE0) iterates slots
  0..7 and calls FUN_008b5d70 using slot for each active slot.
- Slot pointer: `&DAT_018676b0[slot]` (= TkWindow pool, same RVA as
  `tkWinArrayAddr 0x14676B0`).
- Conditionally calls `FUN_008B5F60` (cursor-rect renderer) only when
  slot entry 0x1E equals 1 — that's the gate that limits session-45's hook to a
  narrow set of state transitions; it does NOT fire for general-purpose
  per-frame draws.
- Main draw is the slot's vtable +0x12C method — actual text rendering for
  this slot is here.

### Globals
- `DAT_0112A014` — pre-render callback function pointer (NULL means none)
- `DAT_0112A01C` — message-list base (set by FUN_00777010 from DAT_0112A03C)
- `DAT_0112A024` — string-table base (offsets to text fragments)

### Pipeline split — FUN_00776A50 is NOT the NPC dialogue path (session 52)

Re-read of FUN_0076F580 / FUN_0076F960 in session 52 clarified: those two
renderers walk an **event-message LIST** at `DAT_0112A01C` whose entries
are 0x138 bytes each, with type tags `'\0'`, `'\x01'`, `'\x02'`, `'\x03'`,

## Message Window System (NPC dialogue + system popups + battle text)

The 8-slot message-window pool at `DAT_018676B0` (RVA `0x14676B0`) is
the universal text-display surface for **interactive** game text:
- NPC dialogue (walk up to NPC, press confirm → dialogue box)
- Acquired-item popups
- Yes/No save-load confirms
- Battle help / info / damage / capture / first-strike messages
- Cutscene speech bubbles tied to a TkObjectMessage slot

The same pool drives all of these. The message subtype is stored at slot offset
+8 and selects a per-slot vtable from the table at `PTR_FUN_00C5B1B0`, with a
stride of nine dwords (0x24 bytes).

### Setup function — `FUN_008B8980` (RVA `0x4B8980`) — **universal text installer**

**This is the single function called by every "open message window" path
in the game** to install the displayable text byte stream into a slot.
It is the right hook target for capturing NPC dialogue text.

FUN_008B8980, RVA 0x4B8980, installs text for a slot. Its recorded contract is a slot index and two text-pointer arguments, textPtr_A and textPtr_B; the function has no return value. The following field/lifetime analysis describes how these inputs are retained.
- `slot_idx` (param_1, on stack) — 0..7
- `textPtr_A` (param_2) — original / English / JP byte stream
- `textPtr_B` (param_3) — international / translated byte stream

Behavior:
1. Picks the active variant: textPtr_B when FUN_008AC340 returns one and FUN_00785290 does not return one; otherwise textPtr_A for slot+0x90/0x94, else textPtr_A as the original-language selection for slot+0x5C/0x60. (Most callers pass equal second and third text-pointer arguments, so both halves point to the same buffer.)
2. Writes:
   - slot offset 0x5C receives textPtr_A
   - slot offset 0x60 receives textPtr_A
   - slot offset 0x74 receives chosen_for_intl
   - slot offset 0x78 receives chosen_for_intl
   - slot offset 0x90 receives the pointer at slot offset 0x74 when the FUN_008AC340 language gate is active, otherwise the pointer at offset 0x5C
   - slot offset 0x94 receives the pointer at slot offset 0x78 when the FUN_008AC340 language gate is active, otherwise the pointer at offset 0x60
   - slot offset 0x20 receives 0 (state reset)
   - slot offset 0x22 receives one when FUN_00785270 returns one or DAT_00C59558 holds one, and zero otherwise
3. Calls slot's `vtable[+0xF4]` callback (per-subtype text-format/layout init).

**For announcement, the simplest read is `textPtr_A` (param_2) on
`onEnter`** — every caller is observed to pass the same pointer for
param_2 and param_3 (the international variant divergence only matters
for the rendering pipeline, not for the decoded text content).

Confidence FUN_008B8980 is the universal text installer: **0.95**. Eight
distinct callers in the decompile, all matching the
`(slot, textPtr, textPtr)` shape; field writes match every observed
read site (FUN_008B8D90, FUN_008B9600, FUN_008B9A10, FUN_008DE8A0,
FUN_008DECE0, FUN_008DED40 all read slot+0x94 and walk it as a byte
stream).

### Callers of FUN_008B8980 (representative sample)

- `FUN_00858B30` — battle-window opener (FFX-charset color setup wrapper)
- `FUN_00858B90` — wrapper variant
- `FUN_008589F0` — Atel script "open dialogue with NPC" — pulls

  FUN_0086BE20 using slot, then FUN_008B8980 using slot, psVar8 entry 4, psVar8 entry 6.
  This is the NPC-speech entry from event scripts.
- `FUN_00860D00` (RVA `0x460D00`) — Atel script "open simple message"

- `FUN_00860DE0` (RVA `0x460DE0`) — Atel script variant of the above with
  early-out / cleanup.
- `FUN_0089B0B0` (RVA `0x489B0B0`) — system message wrapper.
- `FUN_0089B140`, `FUN_0089B1A0`, `FUN_0089B200`, `FUN_0089B260` —
  battle-info / battle-status / Yuna-summon / Aeon-info windows.
  Each calls FUN_008B8980 using slot, textPtr, textPtr.

The `FUN_008589F0` caller is the **Atel script bytecode handler that
fires when an NPC dialogue command is decoded from a CHEvent
(namespace 0x5, RVA 0x4891F8) script**. Hooking `FUN_008B8980` (the
single shared point of all setup paths) is more universal than hooking
`FUN_008589F0` and catches both NPC speech AND every other system /
battle / item popup with one hook.

### Why the existing menus.js TkWindow iterator misses NPC dialogue

The hook in `src/menus/menus.js` on `FUN_008ABCE0` iterates all 8 slots
each frame and reads each slot's `winPtr+0x5C` textPtr — which is the
correct byte stream for NPC dialogue. **However, it filters out entries
whose selector flag is set.** As documented in the current-entry layout above,
the flag one byte after the current-entry pointer is the **selector mode flag** —
it is non-zero ONLY for popups that have a cursor / selectable items
(yes/no confirms, item-acquired prompts that require X to dismiss,
etc.). **Pure NPC dialogue with no selector keeps that flag clear**, so
the iterator skips it.

This is why "acquired items" popup (a one-item selector with a
confirm cursor) reads correctly but interactive NPC dialogue does not.

### Recommended hook for NPC dialogue capture

Hook **`FUN_008B8980` (RVA `0x4B8980`)** in `onEnter` and decode
`args[1]` (param_2) with decodeFFXSegments using textPtr, len, 0. One
hook captures every message-window text installation (NPC dialogue,
acquired items, yes/no, battle messages, system popups). This
replaces the existing `FUN_00776A50` hook in `src/menus/dialog.js`
for NPC dialogue purposes, and runs once per message appearance (not
per-frame), avoiding the typewriter-redundancy diff problem
entirely.

### Overdrive minigame state machines (per-character)

Each character with an OD input minigame has a dedicated state-machine
function plus per-character globals for state, success flag, and (for
counter-style minigames) outcome counter. All RVAs verified by reading
the function bodies in
`Docs/Scripts/Ghidra/output/FFX/decompile/layer2_game_logic.txt`.
chrIdx mapping confirmed via the final FUN_007b0480 using chrIdx, ... call
at the end of each handler.

| Character | Mechanism | Handler RVA | State register | Success flag / counter | Anchor string | chrIdx (in FUN_007b0480) |
|-----------|-----------|-------------|----------------|------------------------|---------------|--------------------------|
| Tidus     | Meter-timing — bar oscillates between bounds, press X when bar in target window. | `0x492290` | `0xF3D6F4` (u8) | `0xF3D6B3` (u8, set 1 = success) | `"btidu"` / `"bgood"` | 0 |
| Auron     | Button-sequence matching — press buttons in order; each match increments counter, mismatch resets. | `0x490EE0` | `0xF3D6B4` (u8) | `0xF3D6B2` (u8, set 1 = success) | `"bauro"` / `"bgood"` | 2 |
| Lulu      | Joystick rotation — direction-quadrant tracking, full rotation increments counter; counter caps at `0x10`. Final dispatch passes counter as result (= spell count). | `0x491AF0` | `0xF3D6C8` (u8) | `0xF3D6DF` (u8 counter, max `0x10`) | `"blulu"` / `"bgoodl"` | 5 |

State register values: state machines all follow the same shape — case 1
(init), case 2 (animation wait), case 3 (start input phase), case 4
(input listening — the active minigame), case 5 (success animation; not
present in Lulu since Lulu uses a counter), case 6 (Lulu: time's up,
finalize counter / Tidus+Auron: success animation wait), case 7
(failure path), case 8/9/10 (cleanup, dispatch `FUN_007b0480`).

Forcing success in production (`src/battle/od_success.js`):
- Tidus / Auron: write `1` to success flag, write `5` to state register
  → state machine advances directly to success animation.
- Lulu: write `0x10` to counter, write `6` to state register → state
  machine skips to time-up branch which dispatches `FUN_007b0480` with
  the maxed counter.

### Native C++ rewrite and transition threading

A native x86 reader is feasible. UnX already installs native hooks in this engine,
but that is not proof of speech-thread safety. The other working reader is private;
its implementation is unavailable. The current Git history contains the small
dinput8 proxy and JS reader, not an earlier native reader to recover. The abandoned
managed port does not establish that C++ cannot work.

Session 70 source facts before the Session 71 implementation below:

- `dinput8_proxy.cpp` loads the real dinput8 and Frida Gadget in `DllMain` and
  unloads the former on detach. The Gadget binary is 18,344,448 bytes.
- UnX's `DllMain` records its handle and disables thread notifications. Its
  `DeferredDllMain` installs hooks after initialization through Special K.
- Navigation and battle currently register frame callbacks; the TK pool reader
  also scans on a draw iterator. Those are polling despite earlier documentation
  calling them event-driven. Porting them verbatim would retain their defects.

Recommended ownership model for the port:

1. Keep DLL entry minimal. Initialize speech and hooks from a verified bootstrap
   outside loader lock. Resolving/forwarding DirectInput must remain available
   before the first export call; do not introduce an uninitialized forwarding race.
2. Install x86 hooks once, in a queued batch, with verified ABI signatures. Never
   repeatedly suspend threads or reinstall hooks during map changes.
3. Read game pointers/getters only on the thread executing the native event.
   Decode and copy text/state there. A speech worker owns only copied strings,
   event identities and map-generation numbers; it never dereferences game objects.
4. Invalidate map-generation work when a transition starts. Distinguish a requested
   destination from loaded assets and from completed actor population. The body of
   `FUN_009093b0` loads/installs resource chunks; its return is not proof that all
   actors exist. Verify teardown/actor-create events before choosing lifetime hooks.
5. Protect re-entry with thread-local state, bound queues and instrument owner
   thread IDs, generations and enqueue/dequeue events. Preserve distinct valid
   events, including repeated identical text. Use `Tolk_Output` for speech/braille.
6. Move one validated feature at a time. Disable its JS producer before enabling
   its native producer. Remove Gadget only after the native reader reaches tested
   parity. Session 70 had no native replacement; Session 71's implementation
   checkpoint below records the new vertical slice and its pending live gate.

These address plausible failure modes, not a confirmed diagnosis of the original
transition crash. Microsoft documents loader-lock restrictions in
[DLL best practices](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices).
[MinHook upstream](https://github.com/TsudaKageyu/minhook) documents x86 support and
queued hook installation to reduce repeated thread suspension. The local UnX
reference is GPL; it was inspected, not copied into this implementation.

### Corrected map-exit analysis

The own-game log recorded worker 31, type 2, code length 17,956, destination
room `0x173` (371), spawn 0, followed by speech **Exit to None**. Offline

Fix implemented in `atel.js`, `atelMemory.js`, `roomAreas.js` and `exits.js`:

- Decode instruction boundaries; jump operands index the current worker's jump
  table (`header+0x24`). JSR names another worker's entry zero, not a bytecode PC.
- PUSHI indexes signed integers at `header+0x18`, with count at `+4`. PUSHII is a
  signed immediate. Calls/computation cannot reuse earlier argument literals.
- Analyze all reachable branches conservatively. Name only a unique, fully known
  nonnegative room; ambiguous/computed/malformed routes retain generic Exit labels.
- Warp calls remain Common `0011/010B`. Native wrappers `FUN_008580c0` and
  `FUN_00858370` pop spawn then room and call `FUN_0086fed0`. Their RVAs are
  `4580C0/458370`; earlier allocator claims double-subtracted the image base.
- Translate room to a verified single-area index before using the game's localized
  `FUN_0086c3c0`/`FUN_006460e0` getters. Cache successes only. Do not enumerate area
  tables or invent names for missing/multiple-area mappings.
- Give exits/events their actual `workerIdx`, required by the navigation selection
  identity logic when lists are rescanned or sorted.
