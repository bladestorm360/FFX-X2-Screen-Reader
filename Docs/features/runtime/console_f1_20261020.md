## Request, design and status

The previously deployed October20 DLL was a release build: the console was
compiled out, rather than overwritten by the game. The requested local
development build enables it for Baaj testing. Implementation, native input and
development/release utility checks pass. The warning-free x86 development build

## Controls and game behavior

In the field, close native dialogue, press Shift+F1, type `warp 196 0` and press
Enter. This requests Baaj Ruins — Antechamber, script bjyt1000, entrance0 of two
native entrances. The six seals are in that room. Escape closes the console.
Ordinary warps preserve progression and do not grant destruction-sphere flags
or edit a saved file. The user reports the supplied Summon file was the wrong
save; its Besaid bit does not establish current tester progress.
[Baaj implementation/evidence](../navigation/baaj_seals_20261020.md).

Plain F1 retains the game toggle. Shift+F1 is exclusively reserved in development
builds, including battle/menu/minigame refusal contexts. Only the field can open
the console. Queue pressure can refuse its action but cannot hand F1 to the
game. Release and `--test-build` exclude the console; default
`build_dinput8.bat --no-deploy` stages the requested development flavor.

## Source, ownership and lifetime

`utilities.cpp::installUtilities` registers Shift+F1 with an always-available
capture predicate and explicit exclusive ownership. `consoleKey` checks actual
field context at dispatch. Release preprocessing excludes both registration and
console entry. `events.hpp::hotkeyChordWhen` defaults exclusive ownership Off
for all other chords. `input.cpp::consumeKey` tries the existing64-slot FIFO
once; only an available explicitly exclusive chord remains captured on refusal.
Ordinary handback and generation/revision/focus/Escape/context checks remain.

`input.cpp::received` owns Windows-message suppression on the native owner.
Console activation/focus loss no longer clears captured-key latches. Each key's
repeats and release stay captured until its own release; no new command is
queued while focus/console exclusion applies. `direct_input.cpp::deviceState`
and `deviceData` use the same consume result and existing per-scan held latches.
Buffered Peek recognizes ownership without dispatch; consuming reads own the
command. Releasing Shift cannot reclassify a captured F1 hold as plain F1.

The UI thread, bounded context/reply transport and native action owner remain
unchanged. [Console lifetime/focus](../../console_thread_hardening_20261008.md)
and [DirectInput COM ownership](../../direct_input_ownership_20261012.md) retain
their exact boundaries. Bindings are installed before hooks and immutable
afterward. This repair passes no game pointer to the console thread.

## Evidence, bounds and extension

ownership exposed the separate failure on repeated F1 after console focus.
Both now pass using production input/DirectInput adapters, along with buffered

generation and64-command overload. The FIFO still drains at most64 commands
per qualified return; the new decision is constant work, with no allocation,
scan, timer, retry or native-thread wait.

`utility_fixture.cpp` checks the actual exclusive registration, refusal
contexts, Baaj196/entrance0 selection and rejection of entrance2. Release checks
absence of console/warp entry. Existing original fixture inputs are reused
read-only. The preparation script now stages those inputs and test builds outside
Git through the validated external evidence root. Both utility flavors pass
after migration. [Source boundary](../repository_content_20261020.md).
