## Loading, installation and dependencies

This remains an ordinary uncompressed C#/.NET Framework x86 WinForms EXE with
26 inspectable manifest resources. Seven native/document payloads, the locked
PRISM runtime/licenses, checksums and stock-game inventories are embedded.
Setup reads DLL resources as data, checks hashes and copies them to the selected
game folder. It does not execute its bundled DLLs or download additional code.
The Windows manifest requests asInvoker; normal installation edits files and
launcher XML, and optional launch repair alone requests elevation after the
user chooses it. An unwritable game folder retains the existing explicit
administrator retry. This follow-up changes no game/launcher binary or setting.

Game loading intentionally retains the dinput8 proxy, x86 MinHook and launcher
AppDomainManager integration. Those legitimate accessibility mechanisms are
described in the distribution/runtime topics and are not concealed or replaced.
Optional IFEO launch repair/restore retains its five-image scope, installed-path
filters, preview, explicit confirmation, backup and conflict refusals. Removing
working accessibility/repair features on a speculative detection theory was
rejected. There is no evidence naming IFEO, MinHook or a particular DLL as the
reported trigger.

## Concrete installer changes

`InstallerRuntime.Initialize`, called before WinForms setup/discovery, now uses
SetDefaultDllDirectories with LOAD_LIBRARY_SEARCH_SYSTEM32. Setup needs Windows
native libraries only; its bundled mod/runtime resources remain data. This
excludes loose DLLs beside the downloaded installer, the current directory and
PATH from default native lookup for the life of setup. It is process-local,
does not alter machine policy and fails instead of continuing if the API fails.
The policy applies after managed startup; it does not claim protection before
the CLR entry point or against explicit absolute-path loads by the platform.
The supported Windows platform needs that API (Windows 8+, or the documented
legacy update); current distribution testing is Windows 11/.NET Framework.

`AssemblyInfo.cs` adds the real community publisher bladestorm360, a descriptive
accessibility purpose and informational build identity
1.0.1+installer.20261024. Numeric product/file version remains 1.0.1.0. This is
publisher metadata, not Authenticode trust. Neither the loader change nor added
metadata is claimed to explain or eliminate the original Defender alert.

The original installer has no Authenticode signature. No code-signing certificate
was found in the user's/machine's signing stores. No signing service was
configured or purchased, no tool installed and no self-signed trust introduced.
Trusted signing/timestamping remains an explicit distribution gap. Future
signing must cover mod-owned inner DLLs before embedding and the final EXE
afterward, preserving third-party identities and rechecking all hashes/scans.

## Exact-artifact release gate

`package_release.ps1` calls `verify_distribution_security.ps1` after the final
ZIP is assembled and before replacing any local package. There is no skip
option. It reads the exact final x86 assembly in an x86 host, extracts every
embedded DLL/EXE into an owned evidence folder and scans the EXE, ZIP and all
extracted binaries individually. It uses the active, valid Microsoft-signed
MpCmdRun platform matching the status version, and requires active Defender,
real-time protection, present engine/signature metadata and definitions not
reported out of date. It rereads status afterward and refuses version changes
during the scan. Errors, missing status, unavailable/stale protection and
nonzero scan results block the package. Invalid existing PE signatures block;
unsigned files are recorded honestly rather than presented as signed.

The custom scan uses ScanType 3, DisableRemediation and ReturnHR. Microsoft
documents this per-invocation mode as ignoring exclusions, scanning archives,
listing detections without quarantining files or changing protection settings.
This avoids deleting source/release inputs during diagnosis. Real-time
protection remains enabled and can still act independently. Internal script
hosting uses process-local RemoteSigned to run repository-owned scanner code;
no persistent execution/security policy is edited.

The receipt records each input SHA256/size/signature status, scanner executable,
platform/engine/definition versions, start/end UTC, individual exit codes and
raw output. Hashes are rechecked after scanning. Static scanner success means
no detection reported for those bytes in that invocation, not universal safety,
Edge/SmartScreen reputation acceptance or an installation/runtime verdict.
